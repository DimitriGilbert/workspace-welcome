# Parts reference — the widget/part system

Generated by **P5** (master plan §5 P5) from the part sources on branch `widgets/system`.
This is the compliance-facing companion to the probe surface: for every part it records the
props that matter for placement, the exported `MIN_CONTENT` pixel floor (single source of
truth — the ui component's own export, never restated), the documented **below-min fallback**
(what the widget's `sizes` ladder supplies instead when the box is under the floor), and the
smallest ladder rung that fits the floor at the preview density (96 px cells / 12 px gap —
run boxes 96×96, 204×96, 204×204, 204×300, 312×300).

Live verification surface: the dev route `/parts-preview` renders every part at every rung per
theme scope; `node scripts/widget-check/run.mjs --suite parts-preview` asserts
box ≥ `data-part-min-w/h` at every rendered rung, no horizontal overflow, non-empty token
resolution, and fixed-box == viewport inside each scope.

Two layers, one naming contract (master plan §3.5):

- **Layer 1 — `packages/ui/src/components/`**: presentational, props-in / tokens-only,
  container-query degradation only, headerless. Floors: the `MIN_CONTENT` export.
- **Layer 2 — `apps/web/src/components/parts/`**: context-consuming compositions wrapped by
  `definePart` (`id` + `min` taken verbatim from the wrapped ui child's export). Floors: the
  widget registry's authored `min` rung clamps placement; the part-level px floor is advisory
  and probe-validated.

Min-content negotiation is three-layer (§3.3): registry `min` clamps → `MIN_CONTENT` is
advisory + probe-validated → parts self-degrade within a rung via container queries.

`ThemeScope` (P1) is infrastructure, not a rendered part: it stamps `data-ww-theme` +
`data-theme-scope` and must never create a containing block (no transform/filter/contain/
overflow/z-index/position) — portal content keeps `position: fixed` semantics. The
parts-preview mounts a `[data-fixed-box-sentinel]` per scope so the part-min probe can assert
that contract mechanically (fixed box == viewport).

Dialog parts mount as ui `Dialog`s (portaled into the ThemeScope host by `useThemePortal()`);
closed they render nothing, so their placement story is the widget shell's, not the ladder's.
`/parts-preview` toggles them open and defaults `form-add-root` open in the first scope so the
suite always has a real portal surface to check (portal theme inheritance + fixed-box).

## 3. Ladder geometry (preview density)

| Rung | Box (w×h px) |
|---|---|
| 1x1 | 96×96 |
| 2x1 | 204×96 |
| 2x2 | 204×204 |
| 2x3 | 204×300 |
| 3x3 | 312×300 |

Theme cell density varies 92–104 px (§3.3). A theme's density making a part floor unsatisfiable
at its authored rung is a harness finding (`part-min` FAIL), not runtime behavior — the fix is
the theme's authored ladder, never a part-local copy.
